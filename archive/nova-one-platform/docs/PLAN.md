# خطة Ryko التنفيذية — NOVA-ONE «من الوثيقة إلى منظومة تعمل»

> **المبدأ الحاكم:** كل مرحلة تُنتج قطعة قابلة للاختبار، وتُغلق ببوابة انتقال قابلة للقياس. لا نبدأ مرحلة قبل إغلاق سابقتها بأدلة. كل بوابة مغلقة = وسم (tag) مرفوع فوراً.

**الإصدار:** 1.0 | **التاريخ:** 2026-11-12 | **المرجع المعماري:** [ARCHITECTURE.md](ARCHITECTURE.md)

## 0. التقييم الأولي للخطة (مطلوب قبل التنفيذ)

### 0.1 نقاط القوة (نحتفظ بها كما هي)

| البند | لماذا هو قوي |
|---|---|
| بوابة انتقال لكل مرحلة بمعيار رقمي | يمنع «المنظومة التي تبدو ناجحة» — النجاح يُثبَت ولا يُدَّعى |
| فصل المنفذ عن المراجع (نموذج مختلف عائلةً وحجمًا وسياقًا) | يعالج أخطر انحياز في الأنظمة الذاتية المراجِعة |
| سجل القطع بعقد واجهة وترخيص وHoldout | يحوّل «التركيب» من فن إلى هندسة قابلة للتراجع |
| Evidence Gate | كل قرار مقبول/مرفوض له أثر قابل لإعادة التشغيل |
| ما أُلغي (التدريب من الصفر) + GPU بالساعة | يوازن الطموح مع كلفة واقعية |

### 0.2 المخاطر التكتيكية التي تعالجها هذه الوثيقة

| الخطر | المعالجة المعتمدة هنا |
|---|---|
| لا يوجد GPU/نموذج حقيقي في بيئة العمل الحالية | **استراتيجية Mock-First:** كل واجهة قطعة تُبنى وتُختبر مكثفاً فوق مزيّد حتمي offline، ومزوّد OpenAI-Compatible (vLLM/أي نقطة نهاية) جاهز للوصل دون تغيير الكود — عقد الواجهة واحد |
| تضارب الأدوار الخمسة بفريق من شخص واحد | أدوار تُفصل **هيكلياً في الكود**: قطعة المنفذ لا يمكن أن تكون قطعة المراجع (يفرضها الحل نفسه ويبعث بفشل صريح) |
| الفشل الصامت أثناء التنفيذ | سلسلة تدقيق hash-chain من أول يوم + Evidence Log لكل محاولة |
| تشتت الطموح (64 أسبوعاً) | 3 وسوم أولى صغيرة قابلة للتحقق (v0.1.0 → v0.3.0) تغلق «أسبوعاً 1» كاملاً بأدلة |

### 0.3 قرارات تكيف موثقة (انحراف عن الوثيقة الأصلية بسببه)

1. **Phase 0 يُنفَّذ بأدوات حتمية offline أولاً** — تثبيت vLLM/Qwen مؤجل لحظة توفر العتاد؛ العقد والاختبارات لا ينتظرانه.
2. **الأصول المولّدة تُختبَر بالبذرة** — أي عشوائية في توليد بيانات التقييم يجب أن تكون قابلة لإعادة الإنتاج بايت-ببايت.
3. **حزمة MEDICAL-AI CORE v0 أُرشفت في `archive/medical-ai-v0/`** كأول workload مرشح للمنظومة — بواباتها و529 اختبارها تعمل في CI لكل commit (تثبت أن الحلقة تعمل على مستودع حقيقي).
4. **كل بوابة = وسم git مرفوع فوراً** — الوسوم: `v0.1.0` (البنية)، `v0.2.0` (سجل القطع)، `v0.3.0` (حلقة التحقق MVP).

## 4. المسار الحرج

```
P0: Registry + Harness ──► P1: حلقة التحقق MVP ──► P2: Repo Intel ──► P3: Autonomous
                                                    │
                                                    └──► P4: Verification (متوازٍ) ──┐
                                                                                     ▼
P5: تركيب القطع (يحتاج P1+P2+P4) ──► P6: التقييم التنافسي
```

**التأخير في P1 = تأخير كل شيء.**

## 5. سجل المخاطر

| المخاطرة | الاحتمال | الأثر | التخفيف |
|---|---|---|---|
| تلوث Holdout | متوسط | كارثي | فصل فيزيائي: `holdout/` منفصل الصلاحيات، لا تدريب عليه، مراجعة دورية |
| المراجع يتبع المنفذ | مرتفع | مرتفع | فرض `family != family` في الكود + prompt مختلف + لا يرى سجل المنفذ |
| انفجار تكلفة GPU | متوسط | متوسط | GPU بالساعة + سقف شهري + إيقاف تلقائي |
| قطعة بلا قيمة تركيبية | متوسط | مرتفع | رفض تلقائي إن كان `compositional_delta < +0.10` |
| انحراف المعايير | مرتفع | مرتفع | Evaluation Lead مستقل + Holdout مجمّد + سجل تغييرات |
| تشتت | مرتفع | مرتفع | Sprint أسبوعي + بوابة/وسم لكل مرحلة |
| أمان Sandbox | منخفض | مرتفع | Docker + صلاحيات + مراجعة أمنية قبل P6 |

## 6. القياس — خط أساس لكل قطعة ولكل تركيب

| المقياس | خط الأساس | الهدف |
|---|---|---|
| نسبة نجاح المهام | يُقاس أولاً | +20% |
| التكلفة/مهمة ناجحة | يُقاس أولاً | −30% |
| زمن المهمة | يُقاس أولاً | −25% |
| الأخطاء الأمنية | يُقاس أولاً | −50% |
| التعديلات غير الضرورية | يُقاس أولاً | −40% |
| قيمة القطعة التركيبية | يُقاس أولاً | +10% عند الإضافة |

**مصادر:** SWE-bench Verified + Terminal-Bench + LiveCodeBench (إصدار مثبت) + Holdout داخلي 50–100 مهمة مجمّد.

## 7. حوكمة القطع — دورة الحياة

```
اقتراح → draft → تقييم منفرد → تقييم تركيبي → مراجعة مستقلة → approved → إنتاج
                                                    ↘ rejected   ↘ suspended
```

قاعدة الاعتماد الصارمة: `compositional_delta < +0.10` → رفض تلقائي حتى لو كانت القطعة ممتازة منفردة. أي قطعة تخفض أي مقياس رئيسي → Rollback تلقائي.

## 8. قواعد الانضباط الخمس (غير قابلة للتفاوض)

1. لا قطعة تدخل الإنتاج بلا Registry + Holdout + مراجعة مستقلة.
2. المراجع لا يشارك في كتابة ما يراجعه، ولا يرى سجل المنفذ.
3. كل فشل يُصنَّف ويُسجَّل قبل الانتقال — لا فشل صامت.
4. أي قطعة تخفض أي مقياس رئيسي → Rollback تلقائي، بلا نقاش.
5. Holdout مجمّد ومحمي — لا يُلمس إلا بقرار موثق من Evaluation Lead + Owner.
